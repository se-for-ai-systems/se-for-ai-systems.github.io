Week 5 – Observability with Knowledge Graphs

Portfolio 2 due Monday 22 February 2027 · peer review due Wednesday 24 February
Seminar 3 - Friday 26 February 2027, 09:00–16:00, SDU Odense, room U165

Learning Goals

  • Explain what a knowledge graph is: entities, relations and a schema (ontology).
  • Model an AI system as a knowledge graph: components, data sources, datasets, features, model versions and deployments, with their lineage.
  • Use domain semantics (e.g. assets, sensors, observable properties, observations) to give monitoring data meaning.
  • Query the graph to answer observability questions, such as impact analysis ("what is affected if this sensor drifts?") and provenance ("which data trained the model in production?").
  • Relate the graph to the data pipelines that feed it (batch vs. stream) and to data governance (GDPR, NIS2, EU AI Act).

Exercises

  • Before the seminar: Peer-review two Portfolio 2 submissions (see Portfolio & Exam).
  • Core – Reference project: Build a knowledge graph of the reference project: services, datasets and their versions, training runs, model versions and deployments, connected by lineage relations. Query it: which data trained the model in production, and which deployments use a given dataset?
  • Core – Reference project: Add the domain: the hydraulic system, its components and sensors, and each load cycle as an observation with its sensor results and the model's prediction. Query it: which predictions and deployments are affected if one sensor drifts?
  • Stretch – Reference project: Replay the dataset as events through an event broker in your namespace and update the graph as observations arrive.
  • Own case: Sketch the knowledge graph of your system: the system and lineage part, the domain part, and three observability questions it should answer. Note where the data comes from (batch or stream), who owns it and which regulations apply. Start Portfolio 3.

Notes

The choice of knowledge-graph technology is open: it can be a library in your own code or a graph database in your namespace. A database image must come from a public registry, and its data must be kept on a volume. If you stream events through a Kafka-compatible broker, run the clients as pods: the broker advertises its in-cluster address, so clients behind kubectl port-forward usually fail to connect. Unfamiliar terms are in the Glossary.
