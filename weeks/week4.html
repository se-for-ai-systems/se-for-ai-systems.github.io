Week 4 – MLOps & GitOps

Software Engineering for AI Systems

Self-study week – reading, slides and exercises.
Portfolio 2 due Monday 22 February 2027.

Learning Goals

  • Describe key MLOps concepts: CI/CD for ML, experiment tracking, model registry and data versioning.
  • Describe the AI model lifecycle (develop, build, test, release) and how it connects to the system lifecycle.
  • Compare continuous delivery and continuous deployment, deployment patterns (rolling upgrade, blue/green, canary) and rollback, and explain version skew.
  • Explain infrastructure as code, idempotence and infrastructure drift, and how GitOps addresses drift.
  • Set up a CI pipeline that tests, builds and publishes an ML service.
  • Version data and models to make training reproducible.
  • Explain the GitOps principles (declarative, versioned, pulled automatically, continuously reconciled) and their trade-offs compared to push-based deployment.
  • Deploy to Kubernetes from a Git repository with a push-based workflow.

Literature

The week follows [Bass et al., 2025] Engineering AI Systems. Read the Bass sections in the order listed. Each exercise below names the section it builds on. Of the lifecycle stages in Bass Ch. 6, this week covers build, release and deployment, and connects them to the model lifecycle in Ch. 5.

  • Required: [Bass et al., 2025] Sec. 2.2–2.3 (DevOps and MLOps background) – in particular the parts of Sec. 2.2.1 on idempotence and infrastructure drift.
  • Required: [Bass et al., 2025] Sec. 5.1.1–5.1.2, 5.1.5 and 5.4 (data management, feature engineering, model registry, release). You read Sec. 5.2–5.3 in week 2.
  • Required: [Bass et al., 2025] Sec. 6.5 (release and deploy: continuous deployment, deployment patterns, rollback, version skew) and 6.6.4 (dynamic model updating).
  • Required: [Bass et al., 2025] Ch. 14 (Case study: Predicting Customer Churn in Banks) – MLflow, a model registry and Kubernetes in a regulated setting.
  • Required: [OpenGitOps] GitOps Principles v1.0.0. Bass does not cover GitOps; it extends the infrastructure-as-code ideas of Sec. 2.2.1.
  • Required: [Huyen, 2022] Designing Machine Learning Systems. Ch. 10 (Infrastructure and Tooling for MLOps).
  • Optional: [Bass et al., 2025] Ch. 12 (Case study: Using a Pretrained Language Model for Tendering) – MLOps from proof of concept to production.
  • Optional: [Huyen, 2022] Ch. 6 (Model Development and Offline Evaluation) – useful for the evaluation gate in CI.
  • Optional: [Breck et al., 2017] The ML Test Score.

Exercises

  • Hands-on: Deploy MLflow in your namespace. Log training runs (parameters, metrics, artifacts) from your laptop through kubectl port-forward and register the best model under an alias (e.g. champion). (Bass 5.1.5, 14.1.4)
  • Hands-on: The image contains code only. At startup the service loads the model from MLflow in your namespace by alias (e.g. models:/<model-name>@champion). Rolling back means moving the alias, or the pinned version in your Helm values. (Bass 6.5.2, Rollback)
  • Hands-on: Create a CI pipeline (e.g. GitHub Actions) that lints, runs unit and data-schema tests, builds the image and pushes it to a public container registry on every push. Add an evaluation gate: fail the pipeline if the model scores below a threshold on a fixed evaluation set. (Bass 6.3, 6.5)
  • Hands-on: Set up Git-driven deployment from your laptop: your Git repository (manifests, Helm values, image tags) is the single source of truth, and a script (e.g. a Makefile target) deploys the committed state to your namespace with helm upgrade --install. Use kubectl diff to detect drift between Git and the cluster: change a resource limit by hand with kubectl edit, detect the change, and remove it by redeploying from Git. A GitOps operator such as Argo CD or Flux would pull and reconcile automatically, but it requires cluster-wide permissions that the course cluster does not grant. (Bass 2.2.1, Idempotence and Infrastructure Drift)
  • Hands-on: Track the training data with DVC so that any model version can be traced back to its data. (Bass 5.1.1)
  • Stretch: In CI, generate a software bill of materials (SBOM) for the image and scan it for known vulnerabilities (e.g. with Syft and Grype, or Trivy). (Bass 5.1.1, 6.3, 6.4)
  • Own case: Describe your CI/CD, deployment and versioning workflow, and whether a GitOps operator would fit your company. Name the triggers that will force a new model version in your case (data drift, new data, changed requirements, detected bias, security issues) and how often you expect them. State whether you need continuous delivery with a human sign-off or continuous deployment, and which deployment pattern you would use. (Bass 5.4, 6.5.1–6.5.2) Finish and submit Portfolio 2.
  • Reading check: Answer Bass 5.6 (how DevOps relates to MLOps, the core components of an MLOps pipeline, how IaC is used in MLOps) and Bass 14.5, question 3 (how a model registry helps with compliance). Discuss on the course Discord server.

Notes

Only namespace-scoped installations work on the course cluster: avoid charts that need CustomResourceDefinitions, operators or ClusterRoles. Run MLflow as a single deployment with a SQLite backend on a persistent volume and --serve-artifacts. CI runs outside the cluster and cannot reach it, so the evaluation gate uses an evaluation set stored with the code, and deployment always happens from your laptop.
