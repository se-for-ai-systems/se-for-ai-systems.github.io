Week 4 – MLOps & GitOps

Self-study week - reading, slides and exercises.
Portfolio 2 due Monday 22 February 2027.

Learning Goals

  • Describe key MLOps concepts: CI/CD for ML, experiment tracking, model registry and data versioning.
  • Describe the AI model lifecycle (develop, build, test, release) and how it connects to the system lifecycle.
  • Explain infrastructure as code and infrastructure drift, and how GitOps addresses drift.
  • Set up a CI pipeline that tests, builds and publishes an ML service.
  • Version data and models to make training reproducible.
  • Explain the GitOps principles (declarative, versioned, pulled automatically, continuously reconciled) and their trade-offs compared to push-based deployment.
  • Deploy to Kubernetes from a Git repository with a push-based workflow.

Exercises

  • Core – Reference project: Deploy MLflow in your namespace. Log training runs (parameters, metrics, artifacts) from your laptop through kubectl port-forward and register the best model under an alias (e.g. champion).
  • Core – Reference project: The image contains code only. At startup the service loads the model from MLflow in your namespace by alias (e.g. models:/hydrawatch@champion). Rolling back means moving the alias, or the pinned version in your Helm values.
  • Core – Reference project: Create a CI pipeline (e.g. GitHub Actions) that lints, runs unit and data-schema tests, builds and pushes the image to a public container registry on every push. Add an evaluation gate: fail the pipeline if the model scores below a threshold on a fixed evaluation set.
  • Core – Reference project: Set up Git-driven deployment from your laptop: your Git repository (manifests, Helm values, image tags) is the single source of truth, and a script (e.g. a Makefile target) deploys the committed state to your namespace with helm upgrade --install. Use kubectl diff to detect drift between Git and the cluster. A GitOps operator such as Argo CD or Flux would pull and reconcile automatically, but it requires cluster-wide permissions that the course cluster does not grant.
  • Stretch – Reference project: Track the training data with DVC so that any model version can be traced back to its data, and scan your image for known vulnerabilities in CI.
  • Own case: Describe your CI/CD, deployment and versioning workflow, and whether a GitOps operator would fit your company. Finish and submit Portfolio 2.

Notes

Only namespace-scoped installations work on the course cluster: avoid charts that need CustomResourceDefinitions, operators or ClusterRoles. Run MLflow as a single deployment with a SQLite backend on a persistent volume and --serve-artifacts. CI runs outside the cluster and cannot reach it, so the evaluation gate uses an evaluation set stored with the code, and deployment always happens from your laptop.
