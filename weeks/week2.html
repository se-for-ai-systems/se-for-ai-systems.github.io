Week 2 – Architecting AI Systems: From Notebook to Code

Software Engineering for AI Systems

Self-study week – reading, slides and exercises.
Portfolio 1 due Monday 8 February 2027.

Learning Goals

  • Describe the AI system lifecycle from design to system test, and how a trained model is wrapped as a service. Release and deployment follow in week 4.
  • Compare distributed architecture styles (client-server, SOA, microservices) and interface styles (REST, GraphQL, gRPC) for AI systems.
  • Specify quality-attribute scenarios for an AI system (e.g. reliability, performance, modifiability).
  • Document an architecture with C4 diagrams and architecture decision records (ADRs).
  • Restructure notebook code into a tested, containerized service, with low coupling between the API and the model so that the model can be replaced without changing the clients.

Literature

The week follows [Bass et al., 2025] Engineering AI Systems. Read the Bass sections in the order listed. Each exercise below names the section it builds on. Bass Ch. 6 organizes the system lifecycle into design, development, build, test, release and deployment, and operation and monitoring. This week covers design through test.

  • Required: [Bass et al., 2025] Sec. 2.1.2–2.1.3 (distributed software architectures and interface styles) – the options behind your C4 container diagram and ADRs.
  • Required: [Bass et al., 2025] Sec. 5.1.3–5.1.4, 5.2 and 5.3 (dividing the data, generating, building and testing the model) – from the exploratory notebook phase to a model wrapped as a tested service.
  • Required: [Bass et al., 2025] Sec. 6.1–6.4 (design, non-AI modules, build and test) – the system lifecycle up to release. Sec. 6.5 (release and deploy) follows in week 4.
  • Required: [Huyen, 2022] Designing Machine Learning Systems. Ch. 2 (Introduction to ML Systems Design).
  • Optional: [Bass et al., 2025] Ch. 3 (AI Background) – a recap of model selection and hyperparameters from your previous module.
  • Required if your case uses an LLM or other foundation model: [Bass et al., 2025] Sec. 4.4–4.5 (customizing FMs, designing a system using FMs).
  • Optional: [Bass, Clements & Kazman, 2021] Software Architecture in Practice. Quality-attribute scenarios and tactics.
  • Optional: [Brown] The C4 model. [Nygard, 2011] Documenting Architecture Decisions.
  • Optional: [EU, 2024] Regulation (EU) 2024/1689 (AI Act), Art. 5, Art. 6 and Annex III – needed for the risk classification in Portfolio 1.

Exercises

  • Hands-on: Refactor your notebook into a Python package (src/ layout, pyproject.toml) with separate data, training and inference modules. Let the inference module act as the intermediary between the API and the model, so that a new model version does not change the API. (Bass 5.1.4, 6.1.3)
  • Hands-on: Add unit tests (pytest) for preprocessing and the model's input/output contract, covering common, edge and negative cases, and fix the random seeds so the tests are repeatable. Evaluate the model per class or segment, not only overall. If your observations are correlated (e.g. from the same machine or site), split the data by time or block, not randomly. (Bass 5.1.3, 5.3, 6.2)
  • Hands-on: Serve the model with FastAPI (/predict and /health), write a Dockerfile (start from a slim Python image with CPU-only libraries), and build and run the image locally. (Bass 5.2, 6.3)
  • Own case: Write 3–5 quality-attribute scenarios (at least one about model quality), draw C4 context and container diagrams, write at least two ADRs and classify the system under the EU AI Act. Base at least one ADR on a trade-off from Bass 2.1.2–2.1.3, 5.2 or 6.1.2 (e.g. architecture or interface style, the model as a library call or as a separate service, or what not to package as a microservice). Finish and submit Portfolio 1.
  • Reading check: Answer Bass 6.8, questions 1 and 2 (must a system pass all tests before production; why repeat the unit tests in the system test?). Discuss on the course Discord server.
