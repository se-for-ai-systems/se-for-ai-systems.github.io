Week 3 – The Cloud Continuum

Portfolio 1 due Monday 8 February 2027 · peer review due Wednesday 10 February
Seminar 2 - Friday 12 February 2027, 09:00–16:00, SDU Odense, room U165

Learning Goals

  • Explain the cloud continuum (edge, on-premises, cloud) and reason about where AI workloads should run.
  • Explain virtualization, containers, orchestration, autoscaling and service discovery for ML workloads.
  • Apply reliability tactics (health checks, redundancy, circuit breakers, graceful degradation) and performance trade-offs (latency, throughput, resource mapping).
  • Design a secure infrastructure with heterogeneous compute nodes.
  • Handle requirements on data sovereignty and their impact on architecture.

  • Reference project: Push your image to a public container registry (e.g. Docker Hub or GitHub Container Registry; see Before you push below) and deploy it to your namespace with a Deployment and a Service. Add readiness and liveness probes on /health, run multiple replicas, and kill a pod to observe recovery.
  • Reference project: Add resource requests/limits, move configuration to a ConfigMap/Secret, and restrict traffic with a NetworkPolicy.
  • Own case: Decide where each component should run (edge, on-premises or cloud). Which data may not leave the company or the country? Which existing systems must it integrate with? Compare one managed or vendor platform with self-hosting (build vs. buy). Start Portfolio 2.

Notes

Before you push

  • On an Apple Silicon Mac, build for the cluster's architecture: docker buildx build --platform linux/amd64 .... Otherwise pods fail with exec format error.
  • GitHub Container Registry packages are private by default – make the package public, or the pod fails with ImagePullBackOff.
  • Keep images small: a slim Python base image and CPU-only libraries (aim for under 1 GB).
  • Tag images immutably (e.g. the Git commit SHA), not only latest.
  • Never put company code, data or model weights in a public image.

Pods have no internet access: everything a container needs at runtime (libraries, model files, data) must be in the image or copied into the cluster (e.g. kubectl cp to a volume). A NetworkPolicy that denies all egress also blocks DNS – allow port 53 to the cluster DNS, or service names stop resolving.
